=head1 NAME

RPi::WiringPi::INTERRUPTS - interrupt (edge event) usage examples for RPi::WiringPi

=head1 DESCRIPTION

A practical, runnable guide to handling GPIO interrupts (edge events) with the
object-oriented L<RPi::WiringPi>. The interrupt API described here is built on
C<WiringPi::API> 3.18 and verified on Pi 5 hardware; the snippets run as written.

This document is B<edge-only and uses no> C<use threads> - general
concurrency/worker examples (C<< $pi->worker >>) live in
L<RPi::WiringPi::WORKERS> / C<docs/examples/threads-examples.md>. Callbacks fire in your
own interpreter when you service dispatch, so they work on B<any> Perl, threaded
or not.

This is the C<perldoc> form of C<docs/examples/interrupt-examples.md>. See L<RPi::WiringPi>
for the per-method reference, and the underlying L<WiringPi::API> for the
low-level functional API.

=head1 THE MODEL

Interrupts are B<armed on a pin> and B<driven from the Pi object>:

=over 4

=item *

B<Arm> on a pin object: C<< $pin->set_interrupt(...) >> or
C<< $pin->background_interrupt(...) >> (see L<RPi::Pin>).

=item *

B<Drive and control> dispatch on the Pi object C<$pi>: C<wait_interrupts>,
C<run_interrupt_loop>, C<dispatch_interrupts>, C<auto_dispatch_interrupts>,
C<stop_interrupts>, C<last_interrupt>, C<interrupt_buffer>, C<interrupt_dropped>,
C<background_interrupts>.

=back

The split is deliberate: arming concerns a single pin, but the dispatch queue and
signal wiring are B<process-wide> (one shared event pipe), so those live on
C<$pi>, not on individual pins.

B<The #1 gotcha:> as of C<WiringPi::API> 3.18 a callback does B<not> auto-fire.
It runs in I<your> interpreter only when you service dispatch. So after arming you
must drive dispatch (a loop, or C<auto_dispatch_interrupts>, or a background
process). The callback B<must be a code reference> - string sub names are no
longer accepted.

=head1 ABOUT THESE EXAMPLES

=over 4

=item *

B<Interrupts never require> C<use threads>. wiringPi runs its own C threads
internally and writes events to a pipe; your Perl reads that pipe. Hands-off
handling uses an in-process signal (scenario 6) or a forked process
(scenarios 7-8) - never threads.

=item *

B<Arm on> C<$pin>B<, drive on> C<$pi>. Get a pin with C<< my $pin = $pi->pin($n) >>,
set its mode with C<< $pin->mode(INPUT) >>, then arm it. Everything that touches
the shared dispatch queue lives on C<$pi>.

=item *

B<Callbacks receive> C<($edge, $timestamp_us)> - the edge that fired
(C<EDGE_FALLING>=1 / C<EDGE_RISING>=2 / C<EDGE_BOTH>=3) and a microsecond
timestamp.

=item *

B<The callback must be a code reference> (C<< sub { ... } >> or C<\&handler>) -
string sub names are no longer accepted.

=item *

B<Edge and mode constants> come from C<RPi::Const qw(:all)> - C<EDGE_RISING>,
C<EDGE_FALLING>, C<EDGE_BOTH>, and C<INPUT>. Used by name throughout (no bare
C<1>/C<2>/C<3>).

=item *

B<To hide the most work, prefer the hands-off options.>
C<auto_dispatch_interrupts> (scenario 6) fires callbacks in your own process with
no loop; C<background_interrupts> (scenario 8) runs handlers in their own process.
Sections 1-5 (cooperative) explain the explicit dispatch model that 6 and 8 hide -
read them to understand what happens under the hands-off calls, but B<most
programs only need 6 or 8.>

=item *

For B<running> background work (not reacting to edges), see C<< $pi->worker >> in
L<RPi::WiringPi::WORKERS>.

=back

=head1 DECISION GUIDE

None of these need C<use threads>. To hide the most plumbing, prefer the first
(hands-off) entries.

B<6 vs 7/8 in one line:> C<auto_dispatch_interrupts> (6) gives you lock-free
shared state but I<defers> during a long non-yielding C call;
C<background_interrupt(s)> (7/8) fire regardless of what main is doing but
B<can't touch main's variables>. No long C calls? Pick 6. Long C calls? Pick 7/8.

=over 4

=item *

Attach a handler and forget it; it updates my program's state - scenario B<6>
(C<auto_dispatch_interrupts>).

=item *

Independent handler that fires even during long/blocking work - scenario B<7>
(C<background_interrupt>).

=item *

The same, but several pins in one background process - scenario B<8>
(C<background_interrupts>).

=item *

React to a pin while running my own loop, on my terms - scenario B<1>.

=item *

A program whose only job is reacting to pins - scenario B<2>.

=item *

Several pins, each with its own handler - scenario B<3>.

=item *

Specific edges / debounce a noisy input - scenario B<4>.

=item *

Tear down or clean up on exit - scenario B<5>.

=back

=head1 REACTING TO INTERRUPTS

=head2 1. Cooperative dispatch in your main loop

B<Why/when:> You already have a main loop and want to control exactly when
callbacks run. Simplest model, works on any Perl - but a callback only fires when
you call C<< $pi->dispatch_interrupts >>, so keep the loop snappy. (Want it fully
hands-off? See scenario 6.)

B<Real-world:> A rover whose main loop steers and reads sensors every tick, while
a front bumper microswitch triggers an obstacle-avoidance routine - serviced once
per loop pass.

B<Main & interrupt:> One thread. The callback runs I<inside>
C<< $pi->dispatch_interrupts >>, so it can read/write any of main's variables with
no locking - but it only fires when main calls dispatch, and it blocks main while
it runs.

Do your own work, and fire any pending interrupt callbacks each pass.

    use strict;
    use warnings;
    use RPi::WiringPi;
    use RPi::Const qw(:all);

    my $pi  = RPi::WiringPi->new;
    my $pin = $pi->pin(18);
    $pin->mode(INPUT);

    $pin->set_interrupt(EDGE_RISING, sub {
        my ($edge, $ts_us) = @_;
        print "pin 18 rising at ${ts_us}us\n";
    });

    while (1) {
        do_other_work();
        $pi->dispatch_interrupts;   # Non-blocking: runs callbacks for any events that arrived
    }

    sub do_other_work {
        # ... your periodic work ...
    }

Tradeoff: if C<do_other_work()> blocks for a long time, callbacks wait until the
next C<dispatch_interrupts>. Conversely, if C<do_other_work()> returns instantly
with nothing to do, this loop B<busy-spins at 100% CPU> - pace it with real
periodic work, a short C<sleep>, or block in C<wait_interrupts> instead
(scenario 2).

=head2 2. Blocking wait loop

B<Why/when:> Reacting to pins I<is> the whole job - there's no other work to do.
The process sleeps efficiently until an edge arrives.

B<Real-world:> A doorbell or panic button - the Pi idles at near-zero CPU until
the button fires, then sends a notification.

B<Main & interrupt:> One thread. Main is blocked in C<wait_interrupts> until an
edge, then runs the callback inline (full access to program state). Main does no
other work while it waits.

When reacting to pins I<is> the program. C<wait_interrupts> blocks until an event
arrives (or the timeout in ms), then dispatches.

    use strict;
    use warnings;
    use RPi::WiringPi;
    use RPi::Const qw(:all);

    my $pi  = RPi::WiringPi->new;
    my $pin = $pi->pin(18);
    $pin->mode(INPUT);

    $pin->set_interrupt(EDGE_BOTH, \&on_change);

    while (1) {
        $pi->wait_interrupts(1000);  # Block up to 1000ms, dispatch whatever fired
    }

    sub on_change {
        my ($edge, $ts_us) = @_;
        print "edge $edge at ${ts_us}us\n";
    }

B<Shortcut.> If the loop is literally just C<wait_interrupts while 1>, call the
built-in helper instead of writing it yourself:

    $pi->run_interrupt_loop(1000);        # Blocks, dispatching, forever
    $pi->run_interrupt_loop(1000, 50);    # ... or until 50 events have fired

It returns the number of events dispatched and stops when
C<< $pi->stop_interrupt_loop >> is called (from inside a callback, or a signal
handler) or after the optional event cap. When nothing is armed it sleeps the
poll interval instead of busy-spinning.

=head2 3. Multiple pins and callbacks

B<Why/when:> Several inputs, each with its own handler, serviced by one loop.
(Same mechanics as 1-2; this just shows the fan-out.)

B<Real-world:> A control panel with Start/Stop/Up/Down buttons, each wired to its
own handler.

B<Main & interrupt:> Still one servicing thread - callbacks run one at a time with
full access to main's state; no callback runs concurrently with another or with
main.

One pipe, one loop, many pins - each with its own callback.

    use strict;
    use warnings;
    use RPi::WiringPi;
    use RPi::Const qw(:all);

    my $pi = RPi::WiringPi->new;

    my %pin;
    $pin{$_} = $pi->pin($_) for (18, 23, 24);
    $pin{$_}->mode(INPUT)   for (18, 23, 24);

    $pin{18}->set_interrupt(EDGE_RISING,  sub { print "button A\n" });
    $pin{23}->set_interrupt(EDGE_FALLING, sub { print "button B\n" });
    $pin{24}->set_interrupt(EDGE_BOTH,    \&sensor);

    while (1) {
        $pi->wait_interrupts(1000);
    }

    sub sensor {
        my ($edge, $ts_us) = @_;
        print "sensor edge=$edge\n";
    }

B<One shared handler for several pins.> The callback only receives
C<($edge, $ts_us)>, not the pin. If you arm the I<same> coderef on multiple pins,
call C<< $pi->last_interrupt >> inside it to recover which pin (and the BCM
number) fired:

    my $cb = sub {
        my $i = $pi->last_interrupt;   # { pin, pin_bcm, edge, status, ts_us }
        printf "pin %d (BCM %d) edge %d\n", $i->{pin}, $i->{pin_bcm}, $i->{edge};
    };

    $pi->pin($_)->set_interrupt(EDGE_BOTH, $cb) for (18, 23, 24);

C<last_interrupt> returns a hash reference describing the most recently dispatched
event (or C<undef> if none yet); it is published I<before> the callback runs, so
the callback can read it.

=head2 4. Edge types and debounce

B<Why/when:> You care about a specific edge, or the input is electrically noisy (a
button) and you want the kernel to suppress bounce so the callback fires once per
press.

B<Real-world:> Counting items on a conveyor with a microswitch (or reading a
rotary encoder) - debounce gives one event per actuation instead of a burst from
contact bounce.

B<Main & interrupt:> Orthogonal to where the callback runs - debounce drops bounce
edges in the kernel before they're ever queued, so fewer events reach your
dispatch point.

Edge constants: C<EDGE_FALLING>=1, C<EDGE_RISING>=2, C<EDGE_BOTH>=3. An optional
argument after the callback sets a B<kernel debounce period> in B<microseconds>
(default 0 = off). wiringPi applies it as a Linux B<GPIO-v2 line attribute> at arm
time, so the kernel drops bounce edges before they reach the pipe - it is I<not> a
hardware debounce.

    use strict;
    use warnings;
    use RPi::WiringPi;
    use RPi::Const qw(:all);

    my $pi  = RPi::WiringPi->new;
    my $pin = $pi->pin(18);
    $pin->mode(INPUT);

    # Debounce a noisy button: ignore repeat edges within 5ms

    $pin->set_interrupt(EDGE_FALLING, \&pressed, 5 * 1000);   # Micros -> millis

    $pi->wait_interrupts(1000) while 1;

    sub pressed {
        print "clean press\n";
    }

=head2 5. Teardown and cleanup

B<Why/when:> You need to stop watching pins, swap a handler at runtime, or clean
up on exit.

B<Real-world:> A handheld with a mode button - swap its handler when switching
screens, and release every line on shutdown.

B<Main & interrupt:> Re-arm and stop run in main and edit the registration; after
a stop the callback can't fire, and re-arming swaps it cleanly (the old listener
is stopped first).

    $pin->set_interrupt(EDGE_RISING, \&handler_a);

    # Re-arm the same pin with a different handler - the old listener is stopped
    # automatically first, so no stacked/duplicate registration

    $pin->set_interrupt(EDGE_RISING, \&handler_b);

    $pi->stop_interrupts;   # Release every armed interrupt, drain + close the pipe

B<Forking and cleanup.> C<< $pi->cleanup >> (called automatically at object
destruction) resets pins B<and> releases armed interrupts (it calls
C<stop_interrupts> for you). It is B<fork-aware>: in a forked child the call is a
no-op, so a child can't reset the parent's pins or tear down its interrupts on
exit.

    $pin->set_interrupt(EDGE_RISING, \&handler);

    # ... later ...

    $pi->stop_interrupts;   # Release every armed interrupt
    $pi->cleanup;           # Full teardown (also releases interrupts)

B<Bursts and dropped edges.> Edges are FIFO-queued in a kernel pipe until you
dispatch them. If a fast source outruns your dispatching the queue fills, and the
B<newest> edges are dropped - never merged, never blocked - and counted, so loss
is never silent:

    my $lost = $pi->interrupt_dropped;   # 0 unless the pipe overflowed

If you expect bursts, enlarge the queue with C<interrupt_buffer($bytes)> (it may
be set before arming and persists across teardown):

    $pi->interrupt_buffer(1 << 20);      # ~1 MiB of queue; returns the granted size
    my $size = $pi->interrupt_buffer;    # Read the current capacity

The kernel rounds up to a page and caps at C</proc/sys/fs/pipe-max-size>. Other
mitigations: dispatch faster, use a background process (scenarios 7-8), or
debounce (scenario 4) to cut the edge rate.

=head1 HANDS-OFF HANDLING (NO DISPATCH LOOP)

=head2 6. Fire with no loop (auto_dispatch_interrupts)

B<Why/when:> The most hands-off in-process option - "attach a handler and forget
it," closest to Arduino's C<attachInterrupt>. The callback runs in I<your> program
(it can read/update your variables, no locking) and fires on its own while your
code runs, with no dispatch loop. Best when a handler must touch your program's
state. Caveat: a long non-yielding C/XS call can delay it.

B<Real-world:> A weather station counting anemometer/rain-gauge pulses into a
counter your main loop reads and uploads every few seconds - the handler updates
your in-program state directly.

B<Main & interrupt:> The callback runs in B<main's interpreter> at op boundaries
(and on interrupted sleeps), so it can read/write main's variables with B<no
locking> - but a long non-yielding C call defers it until that call returns.

C<auto_dispatch_interrupts(1)> wires the event pipe to a signal and installs the
handler for you, so C<set_interrupt> callbacks fire B<automatically, in your own
process>, with no C<dispatch_interrupts>/C<wait_interrupts> loop. It is a
B<process-wide> switch (it affects every armed pin), which is why it lives on
C<$pi>.

    use strict;
    use warnings;
    use RPi::WiringPi;
    use RPi::Const qw(:all);

    my $pi  = RPi::WiringPi->new;
    my $pin = $pi->pin(18);
    $pin->mode(INPUT);

    $pi->auto_dispatch_interrupts(1);   # Callbacks now fire on their own - no loop to write

    my $count = 0;
    $pin->set_interrupt(EDGE_RISING, sub { $count++ });   # Updates your own variable

    while (1) {
        do_main_work();        # The callback fires between ops, and during the sleep
        print "edges so far: $count\n";
        sleep 1;
    }

    sub do_main_work {
        # ...
    }

No dispatch loop, no fork, no threads - and the callback shares your program's
state directly. The one caveat: a long, non-yielding C/XS call delays the callback
until it returns (it fires at Perl's safe points). To fire even during such work,
use scenario 7 or 8.

B<Choosing the signal.> By default the pipe is wired to C<SIGIO>. If your program
already uses C<SIGIO>/C<O_ASYNC>, pass a different signal so they don't clash:

    $pi->auto_dispatch_interrupts(1, 'USR1');   # Deliver via SIGUSR1 instead

    # Turn it off again:

    $pi->auto_dispatch_interrupts(0);

B<Opt in while arming.> Instead of a separate C<auto_dispatch_interrupts(1)> call,
you can turn it on as part of C<set_interrupt> - this enables the same
process-wide switch:

    $pin->set_interrupt(EDGE_RISING, sub { $count++ }, { auto_dispatch => 1 });
    # or pick the signal:  { auto_dispatch => 'USR1' }

=head2 7. A background process (background_interrupt)

B<Why/when:> True fire-while-busy with zero servicing, even during long blocking
work - because the handler runs in a I<separate process>. Best for B<independent>
handlers (drive a pin, log, notify) that don't need your main program's variables.

B<Real-world:> An emergency-stop button that drops a motor relay immediately - it
must fire even while main is mid-way through a long upload or computation, and the
handler just drives a GPIO.

B<Main & interrupt:> The callback runs in a B<separate process>, truly
concurrently - it fires even while main blocks, but B<cannot> see or change main's
variables (separate memory; share via IPC). Neither can corrupt the other.

C<< $pin->background_interrupt >> forks a child that runs the handler on each edge
while your main program does anything it likes. The handler runs in the child, so
it B<can't> touch your main variables - use it for independent work (drive a pin,
log, notify).

    use strict;
    use warnings;
    use RPi::WiringPi;
    use RPi::Const qw(:all);

    my $pi  = RPi::WiringPi->new;
    my $pin = $pi->pin(18);
    $pin->mode(INPUT);

    my $h = $pin->background_interrupt(EDGE_RISING, sub {
        my ($edge, $ts_us) = @_;
        # Runs in the background on each rising edge - independent work only
    });

    # main carries on; the handler fires on its own

    for (1 .. 10) {
        do_other_work();
        sleep 1;
    }

    $h->stop;        # stop + reap (idempotent); $h->pid / $h->running too

    sub do_other_work {
        # ...
    }

No C<pipe>, no C<fork>, no C<select>, no C<waitpid> - the library owns all of it
(and an C<END> hook reaps the child even if you forget C<stop>). C<< $h->stop >>
is B<idempotent>: safe to call more than once, and safe after the child has
already exited.

B<Reporting values back (the> C<results> B<channel).> For a handler that just
needs to report a value to the parent, enable the results channel and I<return> a
value from the handler; the parent drains it:

    my $h = $pin->background_interrupt(EDGE_RISING, sub {
        my ($edge, $ts_us) = @_;
        return "$edge\@$ts_us";          # Returned to the parent
    }, { results => 1 });

    while (defined(my $msg = $h->read)) {   # Non-blocking drain in the parent
        print "handler said: $msg\n";
    }

    # $h->fh is the read filehandle, for select / IO::Select

This results channel is identical to C<< $pi->worker >>'s C<< { results => 1 } >>
(see L<RPi::WiringPi::WORKERS>).

=head2 8. Many pins in one background child (background_interrupts)

B<Why/when:> You want background handling (scenario 7) for I<several> pins, but a
separate child per pin is wasteful. C<< $pi->background_interrupts >> forks B<one>
child that services them all, and lets you arm/disarm individual pins at runtime.
Because it spans several pins it lives on C<$pi>.

B<Real-world:> A control box with several buttons and sensors, all handled off the
main program in a single helper process.

B<Main & interrupt:> Each callback runs in the one shared child (separate memory
from main, as in scenario 7). The callbacks are fixed when the child forks -
C<fork> can't carry new code - so C<arm>/C<disarm> only toggle pins registered in
the initial call.

    use strict;
    use warnings;
    use RPi::WiringPi;
    use RPi::Const qw(:all);

    my $pi = RPi::WiringPi->new;
    $pi->pin($_)->mode(INPUT) for (18, 23);

    my $h = $pi->background_interrupts(
        [18, EDGE_RISING, \&on_button],
        [23, EDGE_BOTH,   \&on_sensor, 5 * 1000],   # Optional debounce (us)
    );

    # ... main does its own thing; both pins are handled in the one child ...

    $h->disarm(23);   # Stop servicing pin 23 (the child keeps running for pin 18)
    $h->arm(23);      # Resume it
    $h->stop;         # Tear down and reap the single child

    sub on_button { ... }
    sub on_sensor { ... }

The handle has the same C<stop>/C<pid>/C<running> as scenario 7, plus
C<arm($pin)>/C<disarm($pin)>. The callbacks are fixed when the child forks, so
C<arm>/C<disarm> only toggle pins that were in the initial list (arming an
unregistered pin croaks).

=head1 ANTI-PATTERNS TO AVOID

=over 4

=item *

B<Forgetting to service dispatch in cooperative mode.> If you never call
C<< $pi->dispatch_interrupts >>/C<< $pi->wait_interrupts >>, callbacks never fire -
there is no background process doing it for you unless you set one up
(scenarios 6-8).

=item *

B<Passing a string sub name as the callback.> Only a code reference
(C<< sub { ... } >> or C<\&handler>) is accepted now.

=item *

B<Forking> I<after> B<arming interrupts.> wiringPi's ISR pthreads don't survive
C<fork>, and a mutex held at fork time is left locked in the child. Let the library
do the forking for you (scenarios 7-8).

=item *

B<Relying on> C<auto_dispatch_interrupts> B<during a long non-yielding C/XS call.>
Its callbacks fire at Perl's safe points (op boundaries, interrupted sleeps); a
long C call that never yields delays them. Use a background process (scenarios 7-8)
if a handler must fire during such work.

=item *

B<Enabling> C<auto_dispatch_interrupts> B<when your program already uses>
C<SIGIO>B</>C<O_ASYNC>B<.> It claims that signal; pick one owner, or choose a
different delivery signal (e.g. C<< $pi->auto_dispatch_interrupts(1, 'USR1') >>).

=item *

B<Busy-spinning a> C<do_work + dispatch> B<loop.> A
C<< while (1) { do_other_work(); $pi->dispatch_interrupts } >> (scenario 1) burns
100% CPU if the work returns instantly. Pace it, sleep, or block in
C<wait_interrupts> instead.

=back

=head1 METHOD REFERENCE

Arming methods live on a B<pin> object (C<< my $pin = $pi->pin($n) >>):

=over 4

=item C<< $pin->mode($mode) >>

Set pin mode (C<INPUT> / C<OUTPUT>).

=item C<< $pin->set_interrupt($edge, $cb [, $debounce_us] [, \%opts]) >>

Arm an interrupt; C<< $cb->($edge, $ts_us) >>. C<\%opts> may include
C<< { auto_dispatch => 1 | $signal } >>.

=item C<< $pin->background_interrupt($edge, $cb [, $debounce_us] [, \%opts]) >>

Handle it in a forked child; C<\%opts> may include C<< { results => 1 } >>; returns
a handle (C<stop>/C<pid>/C<running>/C<read>/C<fh>).

=back

Dispatch and control methods live on the B<Pi> object (C<$pi>):

=over 4

=item C<< $pi->wait_interrupts($timeout_ms) >>

Block until an edge/timeout, then dispatch.

=item C<< $pi->run_interrupt_loop($timeout_ms [, $max]) >> / C<< $pi->stop_interrupt_loop >>

Built-in blocking dispatch loop.

=item C<< $pi->dispatch_interrupts >>

Non-blocking: run pending callbacks, return count.

=item C<< $pi->auto_dispatch_interrupts($bool [, $signal]) >>

Fire callbacks automatically, in-process (no loop).

=item C<< $pi->background_interrupts([$pin, $edge, $cb [, $deb]], ...) >>

One shared child for many pins (+ C<arm>/C<disarm>).

=item C<< $pi->last_interrupt >>

Hashref of the most recent dispatched event
(C<{pin, pin_bcm, edge, status, ts_us}>).

=item C<< $pi->interrupt_buffer([$bytes]) >>

Get/set the event-queue capacity.

=item C<< $pi->interrupt_dropped >>

Running count of edges dropped on queue overflow.

=item C<< $pi->stop_interrupts >>

Release every armed interrupt.

=item C<< $pi->cleanup >>

Full teardown (resets pins and releases interrupts; fork-aware).

=back

Edge constants (C<EDGE_FALLING>=1, C<EDGE_RISING>=2, C<EDGE_BOTH>=3) and C<INPUT>
come from C<RPi::Const qw(:all)>.
