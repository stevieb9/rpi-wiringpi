- Fix 4: problem discovered during V8 — rpi-lcd `new()` guarded setup on `$ENV{RPI_PIN_SCHEME}`, which nothing in the ecosystem sets or reads (standard is `RPI_PIN_MODE`, per WiringPi.pm:38/Core.pm:97/rpi-pin). - Fix 3: problem discovered during V7 — rpi-pin's t/40 passed the interrupt callback as the string `'main::handler'` (old API contract; new API + Pin.pm croak on non-CODE) and asserted counters without ever dispatching (new self-pipe model queues until dispatch); fixed with `\&main::handler` + `$pin->wait_interrupts(500)` before each assertion, mirroring rpi-wiringpi t/200. t/15 hardcoded PWM alt `2` (ALT5, Pi 1-4); on Pi 5 GPIO18 PWM is ALT3 (`7`) — assertion now accepts both. Resolved 2026-06-10 as part of V7.
- Fix 2: problem discovered during V2 — `rpi-spi rw():35,37` bracketed the SPI transfer with `pin_mode($cs, 0/1)` (flips pin INPUT/OUTPUT → CS floats mid-transfer) where the intent — per `new()` establishing OUTPUT + idle-HIGH and the 0/1 args — was level writes. Translated to `digitalWrite($cs, 0/1)` rather than mechanical `pinMode`, fixing the latent bug in the previously-dead bit-bang path. Resolved 2026-06-10 as part of V2.
